# Limitations and appropriate use

Every bullet below is true for this branch (session 5: rule mode, chapter 11, a third case and chapter 12). Counts are the ones `npm run verify` prints.

- **Not Google's engine.** The parser and executor implement a documented subset of YARA-L 2.0 Search, and `site/engine/rules.js` a documented subset of YARA-L 2.0 rules. Valid Google syntax outside either subset is reported as "not run here", separately from mistakes. Passing here does not prove a query or a rule compiles in a tenant; nothing has been run in one.
- **Rule mode is a model of the rule engine, not the engine.** A rule here is `rule name { meta: ... events: ... match: $key over N  outcome: ... condition: ... options: ... }` with at least `author`, `description` and `severity` in `meta`, every field on an event variable, one to four match keys over a sliding window of at most 48 hours, the Search aggregates in `outcome`, a mandatory `condition` (`$e`, `#e`, outcome comparisons, `and`/`or`/`not`) and `allow_zero_values` as the only option. The trainer slides each key's window from its first unconsumed event and reports one detection per key per window hit; Google's engine evaluates windows as events arrive and may place a detection at a different moment. Google's own page says Search and rules run on different engines, evaluate different windows and handle repeated fields and deduplication differently, so counts differ; chapter 11 shows the window difference and cannot show the other two on this flat dataset. Not run in rule mode: rules without `match`, non-existence conditions, entity variables, three or more event variables, other options, windows over 48 hours, `by`/`over every` buckets, `dedup`, `order`, `limit`.
- **Rule grading is by test cases, not by the reference.** A rule mission is correct when the learner's rule fires on the authored must-fire key in a window covering the authored minute and produces no detection for the must-not-fire key. Every other detection is counted as a false positive and shown, never scored. Two rules with different thresholds can both pass; the reference is one tuning that does.
- **The data-table join in a rule reads the first matching row.** `$e.field = %table.column` joins an event to the rows whose column holds the field's value; an outcome that reads `%table.other_column` gets the first matching row's value. A tenant's rule engine has its own join semantics and limits; verify there.
- **Flat events.** Real UDM has repeated fields (`security_result`, `principal.ip`, `network.dns.questions`, `network.email.to`). This dataset carries one value per field, so `any`, index syntax and negation-over-repeated-fields behave more simply here than in production, and the Search-versus-rule differences on repeated fields and deduplication cannot be shown.
- **Documentation conflicts.** Google's "Use conditions in search and dashboards" page documents outcome `condition:` and `match: $key over 1h` in Search; the statistics page says Search has no `condition` and does not support `over`. Chapters 6 and 9 teach the documented forms and tell learners to verify in their tenant. In a rule the window is not in doubt.
- **Engine facts follow Google's documentation as verified by the owner (engine v2, 2026-10-18) and by the owner's reviewer (rule mode, 2026-10-18).** The build container cannot reach `docs.cloud.google.com`; the pages are listed in `site/engine/catalog.js` and the facts recorded there and in `docs/EVALUATION.md` are theirs. Specifically: `dedup` between `condition` and `order`, keeping the first row per key; `array` and `array_distinct` cut at 1,000; `earliest`/`latest` on the event timestamp; time functions in `"UTC"` or `"GMT"` only; Search limits of seven `in` tests, four regex and two cidr (rules: ten, five and five, enforced in rule mode); the rule shape, the sliding window, the mandatory condition, `allow_zero_values` and the data-table join form.
- **Reference lists and data tables are bundled, not created.** In a tenant they are objects under Detection > Lists and Detection > Data tables. Google is replacing lists with tables: existing lists migrate automatically and legacy lists retire in July 2027. Search mode runs `in %list` and `in %table.column`; rule mode also runs the join `$e.field = %table.column`. Table rows that fail validation stop the build.
- **Joins follow one of two disagreeing pages.** Two event variables joined by a shared placeholder with `match: $key over 1h`; `over N` means within N of each other, either order; zero values never join as keys (and in rule mode only join when `allow_zero_values` is set); non-existence conditions and three-way joins are not run.
- **Entity context is a bundled directory, not an entity graph.** Each case names its directory file (`content/entities.json` for the station, `content/entities-saltmarsh.json` for the co-operative) and sees the records valid in its window. Field names mirror UDM entity nouns as the team reads them; the values are fiction. Rule mode does not read entity records.
- **Time buckets** in Search mode use fixed clock-aligned windows (`by 5m`); Search's actual bucket alignment and time picker govern real results. **Statistics limits** (90-day lookback, 100,000-row cap, ingestion lag) exist in Google and not here.
- **Scoring is formative.** Hints are free, the last hint is a full answer, progress is editable local state. Nothing here is a credential.
- **The FreeForm page is ungraded by design.** Its structure check reports presence only. Nothing reads it.
- **Three datasets, one engine.** Each case runs against its own file, window, ranges, directory and casebook; the validator proves each file's digest, so an earlier case's answers cannot move when a later one is regenerated. Case 2 is not in time order (two records appended in session 4); the engine sorts. Case 3 uses a second fictional LAN (10.77.3.0/24); the artifact check and the tests accept both.
- **A Log it record ID is now checked against the mission's reference rows, not only for existence** (session 5). An authored ID that drifts to a neighbouring event is a validator error; two such IDs were corrected in this session. On a Read mission, which has no query, existence is still the only check.
- **The Casebook check is structural, not a judgement of quality.** Required fields, `HH:MM` UTC times, record IDs that exist, references that resolve, support for a supported hypothesis, evidence behind a remediation item, no claim words without a record, and the anchors a mission names. A well-formed entry that reasons badly passes. The brief and the engineering bridge grade nothing.
- **Chapter 12 gives less help on purpose.** Its desk missions carry the question, three hints and the Log it, and no explained query parts; a learner who cannot start can still open hint 3.
- **The casebook shortcut depends on the keyboard layout.** `Alt`+`Shift`+`C` is matched on the physical key; on some layouts the combination types a character or switches input language. The Casebook button is the fallback.
- **Notes are yours and only yours.** Session-only unless remembered, bounded at 96 KB, exported only as a local Markdown file you start, never uploaded.
- **No real data, by design.** The datasets come from `tools/gen-data.mjs` with fixed seeds, `.example` domains and documentation IP ranges plus two fictional LANs. Never paste real values here.
- **Accessibility is verified structurally, not with assistive technology.** Playwright asserts names, focus order, heading levels, live regions, the skip link, 320 px reflow and reduced motion; a unit test asserts WCAG AA contrast for every colour token. No session has been run with NVDA, JAWS or VoiceOver.
- **Browser tests run in one engine.** Twenty-seven Playwright tests drive the built `dist/` in Chromium, once at the origin root and once under `/KC7SecOpsClaude/`; there is no Firefox or WebKit run. The recorded runs used Node 22 and an existing Chromium build through `PIER9_CHROMIUM`.
- **Learning effectiveness is unmeasured.** The course has been played end to end by its builders through the grader and the browser; the friction logs in `docs/EVALUATION.md` record what changed as a result. No learner outside the project has used it.
